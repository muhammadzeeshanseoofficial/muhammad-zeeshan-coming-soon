What is Technical SEO? A plain-English guide and checklist

Technical SEO decides whether search engines can find, render and trust your pages. This guide explains what it covers, how each part works and gives you a checklist to start with.

Why Technical SEO Matters

Search engines have to discover a page, fetch it, render it and decide whether it deserves a place in the index before it can rank. Every step can fail.

A misplaced noindex tag, a redirect loop or a JavaScript framework that hides content can quietly remove pages from search.

Technical SEO is also the foundation for AI search. Answer engines rely on the same crawlable, well-structured content.

If Google cannot read your page clearly, an AI assistant is unlikely to cite it.

Crawling and Indexing

Crawling is how search engines discover URLs. Indexing is whether they store them.

The most common problems are:

  • Important pages blocked in robots.txt or tagged noindex

  • Duplicate URLs from parameters, filters and tracking codes

  • Canonical tags pointing to the wrong page

  • XML sitemaps full of redirects, 404s or non-canonical URLs

Start with the Pages report in Google Search Console. It shows which URLs are indexed and why others are not.

Site Architecture

Good architecture keeps important pages within a few clicks of the homepage and connects related pages with descriptive internal links. That helps search engines understand topic relationships and spreads authority to the pages that need it.

Speed and Core Web Vitals

Core Web Vitals measure loading (LCP), responsiveness (INP) and visual stability (CLS). They are a ranking signal and, more importantly, they affect conversions.

Compress images, limit third-party scripts and reserve space for media to avoid layout shifts.

Structured Data

Schema markup describes your content in a machine-readable format: who you are, what you offer, your FAQs, your products. It can unlock rich results and gives AI systems clear facts about your brand.

How Search Engines Process a Page: Technical SEO Step by Step

Before any page can rank, it goes through a pipeline.

Google describes three main stages: crawling, where Googlebot discovers and downloads pages; indexing, where Google analyses the content, renders it and decides whether to store it; and serving, where it selects pages from the index to answer a query.

Technical SEO is the work of removing friction at each of those stages.

Most technical problems can be traced to one of these steps. A page that is never crawled cannot be indexed.

A page that is crawled but renders blank to Googlebot may be indexed with almost no content. A page that is indexed but duplicates ten others may never be chosen to rank.

Thinking in stages makes diagnosis much faster.

Robots.txt, Noindex and the Difference Between Them

Robots.txt tells crawlers which paths they may request. It controls crawling, not indexing: a URL blocked in robots.txt can still appear in search results if other pages link to it, usually without a description.

To keep a page out of the index, allow it to be crawled and use a noindex robots meta tag or HTTP header instead.

A common mistake is blocking a page in robots.txt and adding noindex at the same time. Because the crawler cannot fetch the page, it never sees the noindex.

Another is blocking CSS or JavaScript files that Google needs to render the page properly.

Keep robots.txt short, block only what genuinely should not be crawled (such as internal search results or admin paths), and include a link to your XML sitemap.

Canonical Tags and Duplicate Content

Many sites serve the same content at several URLs: with and without trailing slashes, with tracking parameters, through filters, or in printer-friendly versions. Google groups duplicates and picks one canonical URL to show.

You can influence that choice with rel=canonical tags, redirects, consistent internal links and sitemaps that list only canonical URLs.

Canonical tags are hints rather than directives. If your canonical points to one URL but your internal links, sitemap and redirects all point to another, Google may ignore it.

Consistency across all signals is what makes canonicalisation work.

XML Sitemaps That Help Rather Than Confuse

An XML sitemap lists the URLs you want search engines to know about. It is especially useful for large sites, new sites with few external links and sites with pages that are hard to reach through navigation.

A good sitemap contains only canonical, indexable URLs that return a 200 status code, and is updated when pages are added or removed.

Submit sitemaps in Search Console and reference them in robots.txt. Large sites can split sitemaps by section, such as products, categories and articles, which makes indexing problems easier to spot.

Status Codes, Redirects and Broken Links

  • 200

    The page loaded successfully.

  • 301 / 308

    Permanent redirect; use when a page has moved for good.

  • 302 / 307

    Temporary redirect.

  • 404 / 410

    Not found or gone; fine for pages that no longer exist.

  • 5xx

    Server errors; frequent errors can slow crawling.

Redirect chains, where one redirect leads to another, waste crawl effort and slow users down. Update internal links to point directly at the final URL.

Soft 404s, pages that say not found but return a 200 code, confuse search engines and should return a proper 404 or redirect to a relevant page.

JavaScript SEO and Rendering

Google can render JavaScript, but rendering takes extra resources and can be delayed. Content and links that appear only after scripts run, or only after a user clicks, are at risk of being missed.

Frameworks such as React, Vue and Angular are fine for SEO when important pages are rendered on the server or pre-rendered as static HTML.

To check a page, compare the raw HTML with the rendered HTML using the URL Inspection tool in Search Console.

If key text, headings, links or structured data are missing from the raw HTML and appear only after rendering, consider server-side rendering for those templates.

Make sure links use real anchor elements with href attributes, because search engines follow those reliably.

Mobile-First Indexing

Google predominantly uses the mobile version of a page for indexing and ranking. If your mobile site hides content, structured data or internal links that the desktop version shows, those elements may effectively not exist for search.

Responsive design, where the same HTML adapts to screen size, avoids most parity problems.

Check that text is readable without zooming, buttons and links are easy to tap, nothing overflows the screen horizontally and pop-ups do not block the main content on small screens.

Core Web Vitals in Practice

Core Web Vitals are three measurements of real-user experience. Largest Contentful Paint (LCP) measures how quickly the main content appears; a good target is within 2.5 seconds.

Interaction to Next Paint (INP) measures how quickly the page responds to taps and clicks; aim for 200 milliseconds or less. Cumulative Layout Shift (CLS) measures unexpected movement; aim for 0.1 or less.

The most common fixes are serving correctly sized, compressed images, preloading the main hero image, reducing and deferring JavaScript, removing unnecessary third-party scripts and setting width and height on images and embeds.

Google uses page experience as one of many signals; great content on a slower page can still outrank a fast page with weak content, so treat speed as a way to support content rather than replace it.

HTTPS and Site Security

HTTPS protects users' data and is a lightweight ranking signal. Every page should load over HTTPS, HTTP URLs should redirect permanently to their HTTPS equivalents and internal links, canonicals and sitemaps should all use the HTTPS version.

Mixed content, where an HTTPS page loads images or scripts over HTTP, should be fixed.

URL Structure and Internal Linking

Google recommends simple, descriptive URLs that use readable words rather than long ID numbers, and hyphens to separate words. Keep URLs stable; every change needs a redirect.

Internal links matter at least as much: they help search engines discover pages, understand how topics relate and decide which pages are most important.

Use descriptive anchor text rather than click here, and make sure no important page is orphaned without internal links pointing to it.

Breadcrumbs help both users and search engines understand where a page sits in the site hierarchy, and breadcrumb structured data can display that path in search results.

Structured Data: What It Can and Cannot Do

Structured data uses vocabulary from schema.org, usually in JSON-LD format, to describe what a page is about: an organisation, a product, an article, an event, a recipe, a local business.

It can make pages eligible for rich results, such as product prices or review stars, and it helps search engines understand entities.

Structured data must match the visible content, and eligibility does not guarantee a rich result.

Some features have narrow eligibility; for example, Google currently shows FAQ rich results mainly for well-known authoritative government and health websites, although FAQ markup remains valid.

Validate markup with the Rich Results Test and monitor the enhancement reports in Search Console.

International Sites and Hreflang

If you have versions of pages for different languages or countries, hreflang annotations tell Google which version suits which audience. Each version should list all alternates including itself, links must be reciprocal and each URL should be canonical.

An x-default value can point to a fallback page such as a language selector.

A Technical SEO Checklist You Can Work Through

  1. 01

    Verify the site in Google Search Console and submit your XML sitemap.

  2. 02

    Review the Pages (indexing) report and list important URLs that are not indexed.

  3. 03

    Check robots.txt for accidental blocks of pages, CSS or JavaScript.

  4. 04

    Search the site for stray noindex tags on pages that should rank.

  5. 05

    Crawl the site and fix broken internal links, redirect chains and 5xx errors.

  6. 06

    Make sure every page has one self-referencing canonical, unless it is a deliberate duplicate.

  7. 07

    Confirm HTTP redirects to HTTPS, and one preferred hostname (with or without www).

  8. 08

    Check mobile rendering, content parity and tap target sizes.

  9. 09

    Review Core Web Vitals in Search Console and fix the worst templates first.

  10. 10

    Validate structured data and remove markup that does not match visible content.

  11. 11

    Audit internal links to important pages and add descriptive links where they are missing.

  12. 12

    Set up monitoring so new problems are caught after each release.

Tools for Technical SEO

Google Search Console is the essential free tool: it shows indexing status, crawl stats, Core Web Vitals, structured data reports and manual actions. PageSpeed Insights combines lab tests with real-user data.

A desktop crawler helps map the whole site and find broken links, redirects and duplicate titles. Server logs, where available, show exactly how search engine bots crawl your site.

Tools speed up diagnosis, but each finding still needs judgement about whether it actually matters.

When to Get Help

Many technical basics can be handled in-house, especially on platforms like WordPress or Shopify. Site migrations, large e-commerce catalogues, JavaScript rendering issues, international setups and sudden traffic drops usually benefit from specialist help, because mistakes can be expensive.
